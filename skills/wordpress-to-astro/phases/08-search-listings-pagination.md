# Phase 8: Search, listings, pagination

*Stage 3 (Build), last step: it adds pages and rewrite rules, so re-run the verifier afterwards. Also capture the themed 404 here if it is not already done.*

- When raising search and listings with the user, explain in plain English what the old search and the "load more" and filter behaviour do, why they need a server, and what replaces them (`reference/feature-translation.md`, Search and browsing).
- Identify how search and listings really work before deciding anything: read the page's own embedded component state (for example a Livewire or Alpine component, or a plugin's JSON data) and test the URL parameters with real requests. Document the form or input, parameter names, whether state is held in the URL, and the results URL pattern. Never assume `?s=` or `/page/N/`.
- **Derive every address from what the page's own controls submit, not from the parameter names you noticed.** For each `<form>` and each script that builds a URL (filters, search boxes, sort menus, load-more buttons), serialise it the way a browser would: every named control that is sent, **including text inputs left empty and the default radio button or option**. Clicking one filter submits the whole form, so a form with a type filter and a search box produces `/list/?type=news&q=` (an empty `q`), not `/list/?type=news`. Build the list of submitted addresses as the cross product of each control's values (every option, the empty text value and one non-empty text value, every page index the component can request, with and without the other controls' defaults) and request each one from the live site. Record which empty or default parameters the origin ignores: the new site still has to answer those addresses.
- If the site has search, replace the search backend with a Pagefind index built at Astro build time. Index only the relevant content, using the root selector rather than adding attributes to the markup. The search input and results rendering may use Pagefind, but all surrounding markup and URL patterns stay as served.
- Keep other listing features exactly as they work today: URL-based filters, query-string parameters, category/tag/author archives, and pagination. Mirror the exact URL patterns, including `/page/2/` style paths and `?page=N` query strings, and generate them statically.
- A static host ignores query strings. For listings driven by query strings, fetch each server-rendered variant once (each page of each filter, polite, GET only), generate it as its own page at an internal path, and write host-neutral rewrite rules (`src/data/rewrites.json`: path, exact query parameters, destination). Cover patterns that exist in links even when they are bugs (for example a trailing slash inside a filter value). Write a rule for every submitted address from the step above, **including the forms with empty parameters**. An address no rule matches falls through to the unfiltered page without any error, so check coverage mechanically: every address in the submitted list must resolve on the local review server to content equal to the live response (the re-fetch in `stages/4-verify-and-review.md`, built from two sources as set out in `reference/interaction-checks.md`, section 4). Do not enumerate unbounded values; record the cases not generated. Reproduce each variant's own SEO signals (robots, canonical) exactly as served.
- Features that need a server (live search, in-place filtering, load-more) get **one** client script, loaded the same way on every page, only if the user approved that in Phase 0. Keep it dependency-free, degrade to the static pages if it fails, and log it as a deviation along with the behavioural differences (ranking, reload instead of in-place update). Do not add other markup.
- Record all of this in `docs/url-patterns.md`.
